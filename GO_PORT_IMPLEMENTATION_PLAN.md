# Vanth Go Port and Terminal Monitor Implementation Plan

## 1. Purpose

This is the implementation handoff for replacing Vanth's Python runtime with one native Go executable while preserving the existing Python/`uv` installation and instrumentation experience.

The target product is:

```text
vanth daemon
vanth mcp
vanth monitor
vanth doctor
vanth cleanup
vanth _runner <home> <job-id>
```

The same executable is distributed directly as a native release artifact and inside platform-specific Python wheels. Existing users must continue to be able to use:

```text
uv add vanth
uv run vanth daemon
uv run vanth monitor
uv tool install vanth
```

The Python package remains useful for `vanth.agent_events`, lightweight client helpers, and console-entry wrappers. It must not require a Python interpreter when the directly downloaded native executable is used.

This is a compatibility port, not a rewrite of Vanth's semantics. The hardened Python v1 and its tests are the executable specification until the Go implementation passes the parity gates below.

## 2. Decision and Rationale

Use Go for the native runtime and terminal UI.

Go is a good fit for this project because it provides:

- A small, self-contained native executable without PyInstaller extraction or an embedded Python runtime.
- Straightforward cross-platform process and signal handling through `os/exec`, `os.Process`, and build-tagged platform files.
- Goroutines, channels, timers, and `context.Context` for concurrent stream capture, job waiting, delivery dispatch, maintenance, and graceful shutdown.
- A strong standard HTTP stack and a mature `database/sql` boundary.
- The Go race detector and native fuzzing for concurrency and parser hardening.
- A cohesive terminal stack: Bubble Tea v2, Lip Gloss v2, and ntcharts v2.
- A Tier 1 official Model Context Protocol SDK.

Do not introduce Rust, PyInstaller, Electron, a browser dashboard, or a second persistence layer in this port. Do not split the daemon, MCP server, runner, and monitor into separately shipped binaries. One executable with subcommands is simpler to install, start at login, upgrade, and diagnose.

## 4. Scope

### In scope

- One native Go executable with daemon, MCP, runner, monitor, doctor, and cleanup subcommands.
- Behavioral and on-disk compatibility with the Python v1.
- Direct read-only terminal monitoring through SQLite, with JSONL fallback.
- ntcharts line charts for progress and scalar metric events.
- Direct native release archives for Windows, Linux, and macOS.
- Platform-specific Python wheels containing the native executable.
- Continued `uv` installation and Python `agent_event` compatibility.
- Cross-language conformance tests and a staged cutover.

### Out of scope for this port

- Remote access, TLS, multi-user authorization, distributed workers, quotas, or a web UI.
- Interactive job stdin or PTY supervision.
- A workflow/DAG engine.
- A new event protocol or database schema redesign.
- W&B file-format compatibility.
- Built-in CPU/GPU/memory sampling in the first monitor release.
- Heatmaps, media panes, or a configuration editor in the first monitor release.
- A custom operating-system startup manager. The native binary may be launched by the user's normal startup mechanism; Windows Task Scheduler is not required.

## 5. Compatibility Contract

The Go implementation must preserve these invariants.

### Home and paths

- Resolve home identically in the Python wrapper and Go binary.
- `VANTH_HOME` is canonical.
- `AGENT_BG_HOME` remains a supported alias.
- If both variables are set to different canonical paths, fail clearly before reading or mutating state.
- Resolve symlinks and path case as far as the host platform safely permits before daemon-lock or client comparisons.
- Keep existing names for `jobs.sqlite`, logs, events, backups, locks, and daemon metadata.

### Identifiers, timestamps, and JSON

- Preserve current ID prefixes and uniqueness behavior.
- Store UTC timestamps in the same RFC 3339-compatible textual representation used by Python.
- Preserve JSON field names, nullability, and types at every public boundary.
- JSON object key ordering is not a compatibility promise; semantic equality is.
- Reject NaN and infinities at JSON/event boundaries.

### Job lifecycle

- Preserve all current states and legal transitions.
- Terminal transitions must be compare-and-set operations so competing watcher, runner, stop, timeout, and recovery paths cannot overwrite one another.
- `stop_requested_at` is durable intent, not merely diagnostic metadata.
- A job may become `cancelled` only after the workload tree was terminated successfully.
- Failed termination leaves the job running and the stop operation retryable.
- A runner may publish the workload PID only while `status='running' AND stop_requested_at IS NULL`.
- If PID publication loses that race, the runner must terminate and reap the just-started workload and must not emit `started`.
- Recovery and watcher cleanup failures must not falsely persist a terminal result.

### Delivery semantics

- Keep durable delivery rows, unique `(event_id, target_id)`, leases, claim tokens, attempt history, retry backoff, and at-least-once semantics.
- A crash after an external wake side effect but before the success write remains an explicitly documented ambiguity.
- Do not weaken idempotency IDs or lease validation.

### Security and resource bounds

- Bind the daemon to loopback only.
- Require the current bearer-token mechanism on every protected route.
- Keep request, event-line, log-tail, result, and diagnostic-log bounds.
- Keep single-daemon locking and reject a second daemon without bypass through environment aliases.
- Cleanup dry-run must be read-only, including tombstone handling.
- Unsupported future schema versions must fail closed without mutation.

## 6. Target Architecture

```text
Python package / direct shell
          |
          v
     native vanth executable
       |      |       |
       |      |       +--> monitor: read-only SQLite + JSONL/log tails
       |      +----------> mcp: stdio MCP facade over loopback daemon
       +-----------------> daemon: HTTP + state + runner supervision + delivery
                              |
                              +--> vanth _runner --> workload process group
                              |
                              +--> jobs.sqlite / JSONL / stdout / stderr
                              |
                              +--> Codex app-server or OpenCode CLI wake adapter
```

Use one Go module at the repository root. Start with this deliberately small package layout:

```text
cmd/vanth/main.go
internal/config/          home, limits, version
internal/state/           schema v5, migrations, typed queries, transactions
internal/jobs/            lifecycle, event ingestion, runner supervision
internal/delivery/        claims, retries, adapters
internal/daemon/          loopback HTTP, auth, lock, shutdown
internal/mcp/             MCP tools and daemon client
internal/runner/          private _runner implementation
internal/monitor/         Bubble Tea model, queries, transforms, charts
internal/platform/        process-tree and lock files selected by build tags
src/vanth/                Python compatibility package and wrappers
testdata/                 shared databases, events, protocol fixtures
```

Do not add repository/service interfaces for every package. Use concrete types unless tests or a real second implementation require an interface. Prefer the standard library; add a dependency only for MCP, SQLite, Bubble Tea, Lip Gloss, and ntcharts unless a concrete need is demonstrated.

## 8. CLI and Process Model

### Public subcommands

`vanth daemon`

- Starts the authenticated loopback HTTP daemon.
- Acquires the canonical-home daemon lock.
- Writes the existing daemon discovery/token metadata atomically with restrictive permissions.
- Runs migrations before accepting traffic.
- Reconciles running jobs and expired delivery leases.
- Shuts down gracefully on Ctrl+C, SIGTERM, or Windows service/control termination that reaches the process.

`vanth mcp`

- Runs the MCP stdio server.
- Reuses the official Go MCP SDK.
- Delegates job operations to the daemon over authenticated loopback HTTP.
- Never writes non-protocol diagnostics to stdout; diagnostics go to stderr or the rotating file log.
- Preserve current MCP tool names, input schemas, result shapes, error mapping, and notification behavior.

`vanth monitor`

- Opens the terminal monitor described in section 13.
- Reads state directly and never routes live refresh through MCP.
- Is read-only by default and in the first release. Stop/retry actions are explicitly deferred.

`vanth doctor`

- Reports home resolution, schema, lock/daemon state, database health, artifact availability, stale runners, pending deliveries, and configuration conflicts.
- Supports stable human-readable output and `--json` for automation.

`vanth cleanup`

- Preserves existing cleanup selection, tombstone, and dry-run behavior.
- Supports `--dry-run` with no database, filesystem, or timestamp changes.

### Private subcommand

`vanth _runner <home> <job-id>` is an internal compatibility boundary. It must not appear in normal help. The daemon starts it as a detached process and records `worker_pid`. The runner then starts and owns the workload process group, conditionally publishes `pid`, streams output, parses events, heartbeats, and finalizes the job.

### Compatibility entry behavior

During migration, keep existing Python entry points working. The final Python `vanth` wrapper should execute the bundled native binary and pass all arguments, environment variables, stdio streams, signals, and exit status through. For one transition release, an explicit environment variable may select the legacy Python runtime for rollback; remove it only after the native release has field evidence.

## 9. SQLite and Migration Implementation

### Schema

The first Go release must read and write schema v5 exactly as it exists. Do not add columns merely to make Go code easier.

Tables:

- `jobs`
- `events`
- `wake_targets`
- `deliveries`
- `delivery_attempts`
- `cleanup_tombstones`

Indexes and constraints must match `src/vanth/migrations.py`, including `idx_events_job_seq`, `idx_events_job_type_seq`, `idx_wake_targets_job`, `idx_deliveries_status`, and unique `(event_id, target_id)`.

### Connection policy

For daemon write connections:

- `PRAGMA busy_timeout=5000`.
- `PRAGMA journal_mode=WAL`.
- `PRAGMA foreign_keys=ON`.
- Use short, explicit transactions.
- Use `BEGIN IMMEDIATE` for migrations and operations whose correctness depends on excluding a competing writer.
- Bound the connection pool. SQLite does not benefit from an unbounded pool; begin with one writer connection and a small read pool, then measure.

For monitor connections:

- Open with `mode=ro` and `PRAGMA query_only=ON`.
- Set a bounded busy timeout.
- Do not request a journal-mode change.
- Treat `SQLITE_BUSY` as a transient refresh miss: retain the last valid screen and show a quiet stale indicator.
- A missing database is an empty-state screen, not a crash.
- Read-only WAL mode requires access to the database directory and sidecar files. Test this explicitly.

### Migration safety

- Reproduce migrations 0 through 5 and the pre-migration online backup behavior.
- Refuse `user_version > 5` without changing files.
- Make migration failure atomic and leave the original database usable.
- Name backups compatibly under `backups/`.
- Verify the backup by opening it before reporting migration success.
- Never let the monitor run migrations.

### Typed data boundary

Use concrete Go structs and nullable SQL types where the schema is nullable. Centralize timestamp parsing and JSON validation. Query methods must accept `context.Context`. Keep SQL close to the operation it implements rather than building a generic ORM.

## 10. Concurrency and Lifecycle Design

Use Go's concurrency where it removes polling and makes ownership explicit.

### Root ownership

- `main` creates a root context canceled by OS signals.
- The daemon owns the HTTP server, maintenance loop, delivery dispatcher, in-memory event notifier, and child runner handles.
- Every goroutine must have a documented owner and exit when its owner context is canceled.
- No goroutine may perform an unbounded send. Use bounded channels, nonblocking notification coalescing, or context-aware sends.
- Shutdown waits with a deadline and reports components that failed to exit.

### Event notification

Use a monotonic in-memory notification generation or a close-and-replace channel per job to wake HTTP/MCP waiters after a committed event. The database remains authoritative. Waiters must always re-query after waking so notifications may safely coalesce. Cancellation and timeout must release the waiter immediately.

### Maintenance and delivery

- One ticker-driven maintenance goroutine handles stale runners, timeouts, expired leases, retries, and retention scheduling.
- Delivery claims are transactional and include a unique claim token and lease expiry.
- Use a bounded worker semaphore for external deliveries.
- A worker must verify its claim token before writing completion.
- Network/CLI calls inherit a per-attempt context deadline.
- Retry scheduling uses the existing bounded backoff semantics and is deterministic under a fake clock.

### Runner

- Start stdout and stderr readers immediately after the child starts.
- Use separate goroutines so a full pipe cannot deadlock the workload.
- Incrementally split lines with an explicit maximum event/log line size. Do not use an unbounded `bufio.Scanner` configuration.
- Write durable stdout/stderr and parse `AGENT_EVENT` lines without allowing malformed events to stop log capture.
- Heartbeat from a dedicated ticker until the workload is reaped.
- Wait exactly once for the process and close stream goroutines deterministically.
- Finalize with an atomic status predicate.

### Shutdown

The daemon shutdown sequence is:

1. Cancel root context and stop accepting new HTTP work.
2. Allow active HTTP handlers a bounded drain period.
3. Stop maintenance from claiming new deliveries.
4. Allow claimed deliveries a bounded attempt deadline; leave unfinished claims recoverable by lease expiry.
5. Flush and close diagnostics and database connections.
6. Remove daemon discovery metadata and release the lock only if still owned by this process instance.

Detached job runners and workloads continue across a normal daemon restart. They must not be killed merely because the daemon exits.

## 11. Cross-Platform Process Control

Put platform-specific behavior behind small functions in build-tagged files, not behind a large framework:

```text
internal/platform/process_unix.go
internal/platform/process_windows.go
internal/platform/lock_unix.go
internal/platform/lock_windows.go
```

Required operations:

- Start a runner detached from the daemon.
- Start a workload in a new process group/tree boundary.
- Test process existence without treating permission errors as absence.
- Terminate a workload tree with graceful request, bounded wait, force escalation, and verified exit.
- Reap directly owned child processes.
- Hold an exclusive single-daemon lock for the canonical home.

On Unix, use a new session/process group and signal the negative process-group ID. On Windows, use the appropriate `SysProcAttr` creation flags and a tree-aware termination implementation. Do not assume killing the immediate PID kills grandchildren. Preserve the existing distinction between `worker_pid` and workload `pid`.

The start/stop publication protocol is mandatory:

1. Stop transaction writes `stop_requested_at` while status is running.
2. Stop re-reads the latest workload PID after committing intent.
3. Runner publishes PID only with `status='running' AND stop_requested_at IS NULL`.
4. If intent wins, runner kills/reaps the unpublished workload and exits without `started`.
5. If PID wins, stop sees the PID and terminates the process tree.
6. Only successful termination permits `cancelled`; failure clears stop intent only where the current Python behavior does so and leaves a retryable running state.

Do not weaken the barrier tests that cover both interleavings.

## 12. HTTP, MCP, and Wake Adapters

### HTTP daemon

- Preserve route names, methods, JSON limits, response schemas, and error status mapping.
- Bind only a loopback address selected by the current discovery contract.
- Authenticate before parsing an expensive request body.
- Track active handlers before their worker begins and decrement on every exit path, including thread/goroutine start failure equivalents.
- On shutdown, reject new work and wait for already admitted work up to the configured deadline.
- Apply server read-header, read, write, and idle timeouts; long-poll handlers use their own context semantics.

### MCP

- Map existing tools onto a small daemon client.
- Keep stdio framing isolated from logs.
- Validate tool inputs before HTTP calls and preserve actionable errors.
- Add protocol fixture tests that run the Go MCP server as a subprocess exactly as an agent client would.

### Codex and OpenCode wake delivery

Preserve:

- Codex app-server sequence: `initialize`, `thread/resume`, `turn/start`.
- OpenCode sequence: `opencode run --session <id> --format json <prompt>`.
- Per-attempt timeout, captured bounded diagnostics, attempt history, and lease behavior.
- Delivery idempotency identifiers in the payload so downstream integrations can deduplicate where supported.

Use `exec.CommandContext`; never assemble a shell command string from user data.

## 13. Terminal Monitor and ntcharts Integration

### 13.1 Product behavior

`vanth monitor` is a read-only full-screen TUI. It reads local durable state directly, remains useful when the daemon is down, and never competes for write ownership.

Default layout:

```text
+----------------------+--------------------------------------+
| Jobs                 | Metric charts                        |
| > running  train     | loss                                 |
|   completed eval     | val_loss                             |
|   failed    crawl    | progress.percent                     |
+----------------------+--------------------------------------+
| Selected event table or bounded stdout/stderr tail          |
+-------------------------------------------------------------+
| keys / home / refresh age / read-only status                |
+-------------------------------------------------------------+
```

The model owns only presentation state and a bounded snapshot. Database access runs in Bubble Tea commands and returns immutable messages. `Update` and `View` must never perform SQLite or filesystem I/O.

### 13.2 Event-to-series contract

Continue using `AGENT_EVENT` as the only instrumentation format.

Progress example:

```text
AGENT_EVENT {"type":"progress","data":{"current":10,"total":100,"percent":10,"unit":"epoch","stage":"train"}}
```

Metric example:

```text
AGENT_EVENT {"type":"metric","data":{"_step":10,"loss":0.42,"val_loss":0.51,"accuracy":0.88}}
```

Transform rules:

- Numeric `metric.data` fields become series.
- `_step` supplies x when finite and numeric; otherwise x is event `seq`.
- Ignore other `_`-prefixed keys for plotting.
- Booleans are not numeric metrics.
- Non-numeric fields remain visible in the exact event table.
- `progress.current`, `progress.total`, and normalized `progress.percent` are available as scalar series.
- Preserve `stage`/`phase` as table/filter context; do not silently join unrelated stages into a misleading continuous line. Insert a visual discontinuity when stage changes or x decreases.
- Duplicate x values retain event order. The chart may draw the latest value at a cell, but the table must expose all original events.
- Missing, null, NaN, infinite, or malformed numeric values are skipped and counted in a quiet data-warning indicator.

Use types equivalent to:

```go
type Point struct {
    EventID string
    Seq     int64
    X       float64
    Y       float64
    At      time.Time
    Stage   string
}

type SeriesKey struct {
    JobID  string
    Metric string
}
```

### 13.3 Incremental data loading

- Initial load reads a bounded recent job list and enough recent events to fill the current view.
- Maintain a `lastSeq` cursor per selected/pinned job and query `seq > ? ORDER BY seq` on refresh.
- Refresh around every 250 ms while a visible job is running and around every 1 s when all visible jobs are terminal. Make intervals configurable for tests, not as public complexity in v1.
- Cap each in-memory raw series. The database/event table remains the exact source.
- If SQLite cannot be opened, read the selected job's JSONL event mirror and logs. Clearly label fallback mode and retry SQLite periodically.
- A partial final JSONL line is ignored until complete. Malformed lines produce a bounded warning count, not a crash.
- File rotation, truncation, cleanup, and job deletion reset cursors safely.

### 13.4 Bubble Tea model

Suggested state:

```go
type Model struct {
    width, height int
    jobs          []JobSummary
    selected      int
    pinned        map[string]bool
    metrics       []string
    chartFocus    int
    points        map[SeriesKey][]Point
    lastSeq       map[string]int64
    liveTail      bool
    showLogs      bool
    showEvents    bool
    crosshairX    *float64
    viewMinX      *float64
    viewMaxX      *float64
    loading       bool
    staleSince    *time.Time
    warning       string
}
```

Use typed Bubble Tea messages for refresh results, ticks, log-tail results, and errors. Every asynchronous command must carry a generation number or selection key so a slow result for the previous selection cannot overwrite the current screen.

Request terminal background color through Bubble Tea v2 and choose the matching light/dark palette. Let Bubble Tea/Lip Gloss downsample for lower color profiles.

### 13.5 ntcharts rendering

Use `github.com/NimbleMarkets/ntcharts/v2/linechart` as the rendering primitive, not as the source of truth.

For each visible metric pane:

1. Compute finite x/y domain from visible series after filtering to the view window.
2. Expand a zero-width domain by a small deterministic pad.
3. Construct or resize `linechart.Model` with the pane's cell dimensions.
4. Set quiet x/y label formatters and a small step count based on available width/height.
5. Draw axes once.
6. Clear/redraw series every render from the immutable data snapshot. `Resize` alone does not redraw existing runes.
7. Draw segments with `DrawBrailleLineWithStyle` for density and terminal resolution.
8. Do not connect across missing values, stage changes, x regressions, or deliberate gaps.
9. Draw pinned jobs last. Draw a selected/crosshair point after lines.
10. Compose title, chart, legend, latest-value readout, and warning state with Lip Gloss.

Use one chart per metric. Never use dual y axes. If metric units/scales are incompatible, use separate small multiples.

Downsample before drawing when points exceed roughly twice the chart's horizontal braille resolution. Use a deterministic per-x-cell min/max envelope that retains first, last, minimum, and maximum points in original order. This preserves spikes better than taking every nth point and requires no additional dependency. Unit-test the downsampler against monotonic, spike, duplicate-x, and gap data.

### 13.6 Palette and encodings

Metric identity is the chart title; job identity is the categorical color. Assign a stable slot from a deterministic hash of `job_id`. Collision resolution must be stable for the visible set, and colors must not change when list order changes.

Use at most eight simultaneously visible overlays:

| Slot | Light background | Dark background | ANSI family |
|---:|---|---|---|
| 1 | `#2a78d6` | `#3987e5` | blue |
| 2 | `#1baf7a` | `#199e70` | cyan |
| 3 | `#eda100` | `#c98500` | yellow |
| 4 | `#008300` | `#008300` | green |
| 5 | `#4a3aa7` | `#9085e9` | bright magenta/violet |
| 6 | `#e34948` | `#e66767` | red |
| 7 | `#e87ba4` | `#d55181` | magenta |
| 8 | `#eb6834` | `#d95926` | bright yellow/orange |

Color is never the sole encoding. The selected job also receives a marker or emphasized line style, pinned jobs receive a pin glyph in the legend, and every series is named textually. Fold or hide overlays beyond eight and show `+N hidden`; do not generate more hues.

Job-state colors are separate semantic tokens and always accompanied by text/icon:

- running: animated/static activity glyph plus `running`
- completed: check glyph plus `completed`
- failed: cross glyph plus `failed`
- cancelled: stop glyph plus `cancelled`
- orphaned: warning glyph plus `orphaned`

Do not reuse status colors to identify metric series.

### 13.7 Axes, legends, and exact values

- Keep axes quiet: two to five ticks depending on pane size, compact SI formatting, no unnecessary grid.
- Include units in the chart title or axis label when known.
- Two or more visible series require a legend. A single obvious series does not.
- Sort legends in stable job order, not map iteration order.
- Crosshair snaps to the nearest visible x by binary search over each series.
- Crosshair readout lists the nearest value for every visible job and shows actual x/seq; it must not imply exact alignment where none exists.
- The event table is always reachable and contains exact timestamp, seq, type, level, message, and JSON data.
- Tooltips/crosshair are supplemental; keyboard and table access carry the same information.

### 13.8 Layout and interaction

Required keys:

- `up/down` or `j/k`: move within the focused list/table.
- `left/right` or `h/l` only where they do not conflict with the documented log toggle: change pane/focus or pan the chart; publish the final key map in help.
- `tab`/`shift+tab`: move focus between jobs, charts, and lower pane.
- `enter`: pin/unpin selected job.
- `t`: return charts to live tail.
- `l`: toggle stdout/stderr tail.
- `e`: toggle exact event table.
- `+/-` or `page up/page down`: zoom x around the crosshair/center.
- `[`/`]`: pan x when not in live-tail mode.
- `?`: toggle help.
- `q` or Ctrl+C: quit and restore the terminal.

Mouse:

- Wheel over a chart zooms x around the pointer.
- Click selects a job/chart and positions the crosshair.
- Drag/pan is optional until it proves reliable across supported terminals.
- Mouse behavior must not be the only route to any feature.

Responsive behavior:

- Wide: jobs left, charts right, lower pane full width.
- Medium: compact jobs left and one chart column.
- Narrow: stack jobs, selected chart, lower pane; hide nonessential columns before truncating identifiers.
- Too small: render a stable minimum-size message with current dimensions; never panic or create negative dimensions.

### 13.9 Monitor performance targets

- Key-to-screen response p95 under 50 ms on the reference workload.
- Refresh/render p95 under 100 ms for 8 jobs, 12 metrics, and 100,000 persisted points after downsampling.
- Resident memory remains bounded during a four-hour synthetic stream.
- No database writes, migration, lock acquisition, or journal-mode changes from monitor mode.
- A busy or replaced database does not terminate the TUI.
- Terminal state is restored after normal quit, Ctrl+C, database errors, and panics handled at the program boundary.

## 14. Python and `uv` Compatibility

### Package contents

Keep the Python package and add:

```text
src/vanth/cli.py
src/vanth/_native/<platform>/vanth[.exe]
```

The exact wheel may contain only its platform binary rather than the full directory matrix. Resolve it with `importlib.resources`, not relative current-working-directory paths.

The wrapper must:

- Find the packaged binary reliably in normal installs, editable installs, and `uv tool` environments.
- Replace itself with the native process via `os.execvpe` on Unix where appropriate.
- On Windows, spawn with inherited stdio, forward Ctrl+C as safely as the console permits, and return the exact exit code.
- Preserve environment and arguments without shell interpolation.
- Print one actionable error if the wheel does not contain a binary for the current platform.

Keep `vanth.agent_events` as Python. Existing code that emits `AGENT_EVENT` must require no changes.

### Wheel strategy

Build the same project version into separate wheels for supported targets. The wheels are platform-specific even though the Python wrapper is pure Python because they contain a native executable.

Initial release matrix:

- Windows x86-64.
- Linux x86-64.
- Linux arm64 if CI hardware/emulation validates process behavior.
- macOS x86-64.
- macOS arm64.

Use correct Python wheel platform tags and a Python 3-compatible ABI tag. Validate every wheel in a clean environment using `uv`, not the source checkout. A source distribution may remain for developers, but it must either build the Go binary deterministically with a documented Go prerequisite or fail with a clear unsupported-build message. Do not publish an sdist that silently installs without a native binary.

### Direct releases

Publish checksumed `.zip`/`.tar.gz` assets containing:

- `vanth` or `vanth.exe`
- README/quick-start
- license
- checksums/signature metadata as release policy matures

The direct executable and wheel-contained executable for the same target/version must be byte-identical or produced from the same attested build inputs.

### Versioning

- One version source drives Go `--version`, Python metadata, wheel names, daemon discovery metadata, and release assets.
- Embed version, commit, build time, and dirty marker with `-ldflags`; reproducible release builds should omit or normalize volatile values.
- `vanth --version --json` exposes machine-readable values.

## 15. Testing Strategy

### 15.1 Unit tests

Add table-driven Go tests for:

- Home canonicalization and conflicting aliases.
- Timestamp and JSON compatibility.
- Every legal/illegal job transition.
- Event parsing, oversized lines, invalid UTF-8, malformed JSON, non-finite numbers, and partial lines.
- Delivery claim/lease/retry state transitions with a fake clock.
- Stop intent and conditional PID publication.
- Metric extraction, stage gaps, duplicate/decreasing x, and progress derivation.
- Downsampling spike preservation.
- Stable eight-slot color assignment independent of list order.
- Axis formatting, zero-width ranges, and tiny dimensions.
- CLI argument and error mapping.

### 15.2 Cross-language database conformance

Create checked-in fixtures for schema versions 0 through 5 and representative terminal/running jobs. For each supported OS:

1. Python creates/migrates/writes; Go reads and mutates; Python verifies.
2. Go creates/migrates/writes; Python reads and mutates; Go verifies.
3. Python holds WAL data while Go monitor reads it.
4. Go daemon holds WAL data while Python reads it.
5. Both implementations reject schema 6 without mutation.
6. Backup files open and contain the expected pre-migration state.

Compare semantic rows and events, not raw SQLite bytes.

### 15.3 Differential API/MCP tests

Run the same fixture-driven request corpus against Python and Go daemons and normalize only intentionally variable fields such as IDs, ports, PIDs, and timestamps. Compare:

- HTTP status and error category.
- Response keys and value types.
- MCP tool list and schemas.
- MCP results and protocol error behavior.
- Durable database effects and emitted event order.

Maintain a small allowlist for documented differences; an unreviewed difference fails CI.

### 15.4 Deterministic race tests

Port the existing barriers/failure injection tests, including:

- Stop intent wins before PID publication.
- PID publication wins before stop re-read.
- Workload-tree termination fails, then succeeds on retry.
- Runner finish races stop/recovery/watcher.
- Recovery/watcher cleanup fails without false terminal persistence.
- Daemon shutdown races handler admission/thread start.
- Delivery lease expires while the first claimant is paused.
- Duplicate dispatch/restart does not create duplicate delivery rows.

Use test hooks or injected functions narrowly. Do not add sleeps as synchronization.

### 15.5 Fuzzing

Add native Go fuzz targets for:

- `AGENT_EVENT` line parser.
- HTTP JSON bodies and limit boundaries.
- MCP input decoding.
- JSONL fallback parser.
- Metric extraction/downsampling.
- Home/path environment combinations.

Seed with every known regression. Fuzz tests must assert no panic, no unbounded allocation for bounded input, and stable rejection categories.

### 15.6 Synthetic and chaos workloads

Automate these workloads:

- 50 concurrent jobs, each emitting 500 ordered events; assert exactly 25,000 durable event rows and matching per-job sequence order.
- Mixed stdout/stderr flood with event-shaped garbage, very long lines, invalid UTF-8, no trailing newline, and sudden process exit.
- Workload spawning child and grandchild processes; stop after daemon restart and verify the whole tree exits on Windows and Linux.
- Repeated daemon kill/restart during start, PID publication, event ingestion, delivery claim, cleanup, and shutdown windows.
- SQLite busy/locked windows, disk-full simulation where feasible, read-only directory, missing sidecars, database replacement, and corrupted JSONL tail.
- Delivery endpoint that succeeds, hangs, fails, and succeeds-before-connection-drop to exercise at-least-once ambiguity.
- Monitor workload with 8 pinned jobs, 12 metrics, 100,000 points, x regressions, duplicate x values, huge/small magnitudes, missing values, and rapid resize/input.
- Four-hour bounded-memory soak for daemon and monitor.

All randomness uses a logged seed and produces an artifact bundle on failure.

### 15.7 Monitor tests

- Test `Update` as a pure state machine with synthetic key, mouse, tick, resize, and stale-generation messages.
- Snapshot ANSI-stripped views at wide, medium, narrow, and below-minimum sizes.
- Assert visible cell widths with wide Unicode and combining characters.
- Verify light, dark, ANSI-16, and no-color output paths.
- Verify legend appears for two series, is absent for one, and folds beyond eight.
- Verify crosshair nearest-x results and exact event-table fallback.
- Verify SQLite busy retains the last frame and indicates staleness.
- Run a pseudo-terminal smoke that starts the TUI, resizes, sends keys, quits, and confirms terminal restoration.
- Keep golden files small and reviewable; prefer semantic assertions for data transforms.

### 15.8 Static and dynamic checks

Required CI checks:

```text
gofmt check
go vet ./...
go test ./...
go test -race ./...                  # Linux CI at minimum
go test fuzz smoke with fixed budget
uv run pytest -q
uv run python -m compileall -q src tests examples
uv build
git diff --check
```

Use `uv` for every Python environment and package operation.

## 16. Implementation Phases

Each phase should be a reviewable change and leave both runtimes usable.

### Phase 0: Freeze the contract

- Record current Python behavior and baseline tests.
- Add schema/API/MCP/event fixtures and normalization rules.
- Add a cross-language test harness skeleton.
- Add `go.mod` and the dependency compatibility spike.
- Document the supported platform matrix and Go toolchain version in CI.

Exit gate: dependency spike passes Windows/Linux; fixtures reproduce current Python behavior; no Python behavior changes.

### Phase 1: Read-only Go monitor

- Implement config/home resolution in Go.
- Open schema v5 read-only.
- Implement incremental event transform and JSONL/log fallback.
- Implement Bubble Tea/Lip Gloss layout and ntcharts line charts.
- Add keyboard, mouse zoom, pinning, live tail, event table, and log tail.
- Ship initially as `go run ./cmd/vanth monitor` or a local build; no Python wrapper cutover yet.

Exit gate: all monitor acceptance criteria pass and the Python suite remains green.

### Phase 2: Native state, doctor, and cleanup

- Implement schema v0-v5 migration and backup conformance.
- Implement `doctor` and cleanup with dry-run invariants.
- Add cross-language round-trip tests.

Exit gate: Python/Go database matrix passes on Windows and Linux; future schema rejection is mutation-free.

### Phase 3: Native daemon and runner

- Port auth HTTP, daemon discovery/lock, lifecycle, events, waiters, recovery, shutdown, and resource bounds.
- Port detached runner and build-tagged process-tree control.
- Port delivery claims/retries and wake adapters.
- Port every deterministic hardening regression before adding new behavior.

Exit gate: differential HTTP tests, race tests, process-tree tests, and chaos matrix pass on Windows/Linux.

### Phase 4: Native MCP

- Implement current MCP surface with the official Go SDK.
- Add stdio subprocess conformance tests and fake Codex/OpenCode smokes.
- Verify stdout protocol purity under diagnostics and failures.

Exit gate: existing agent configurations can substitute `vanth mcp` without tool/schema/result changes.

### Phase 5: Packaging

- Add Python delegation wrapper and platform wheel build matrix.
- Build direct native archives from the same artifacts.
- Run isolated `uv` install/tool smokes on every target.
- Add checksum and version consistency checks.

Exit gate: source checkout is absent from every smoke environment and all documented commands work.

### Phase 6: Shadow and cutover

- Make Go the default runtime in pre-release wheels while retaining explicit legacy rollback.
- Run real Codex/OpenCode session smokes and operational soak.
- Compare field diagnostics and resolve unexplained behavioral differences.
- Update service/startup documentation to invoke `vanth daemon` directly.
- Only after the release gates pass, remove the Python server/daemon/runner implementations. Keep Python event/client compatibility.

Exit gate: two consecutive release-candidate matrices pass with no severity-1/2 open defects and rollback is demonstrated.

## 17. Acceptance Criteria

The port is complete only when all criteria below are true.

### Functional parity

- All existing Python tests pass unchanged or have a documented, reviewed replacement.
- Go supports every current MCP tool and HTTP operation with compatible schemas and errors.
- Existing Python-created homes and schema v0-v5 databases open and migrate safely.
- Jobs survive daemon restart; recovery produces the same terminal semantics.
- Events, log files, wake targets, delivery attempts, tombstones, cleanup, and doctor behavior remain durable and bounded.
- Stop/start race regressions pass deterministically.
- Codex and OpenCode fake-adapter tests pass; opt-in real smokes are recorded for the release candidate.

### Platform behavior

- Windows and Linux process-tree stop tests prove child and grandchild termination after daemon restart.
- macOS basic daemon/runner/MCP/monitor smokes pass on both released architectures.
- A second daemon cannot start for the same canonical home through either environment alias.
- Ctrl+C/SIGTERM restores terminal state and leaves recoverable durable state.

### Monitor

- Reads SQLite without writes or migrations and continues while the daemon is down.
- Correctly charts metric fields and derived progress values using `_step` or event sequence.
- Does not connect lines across stages/gaps/x regressions.
- Supports job selection, pinning, zoom, pan/live-tail reset, crosshair, event table, and log tail by keyboard.
- Mouse wheel/click work where terminals support them, with full keyboard equivalents.
- Uses stable job colors, a legend for overlays, secondary encodings, and no more than eight visible overlays.
- Handles narrow terminals, no-color terminals, large/empty/invalid data, SQLite busy, deletion, and file rotation without panic.
- Meets the response, render, and bounded-memory targets in section 13.9.

### Distribution

- Direct native artifacts run without Python, Go, or network access after download.
- Platform wheels install in clean environments with `uv` and expose `vanth daemon`, `vanth mcp`, and `vanth monitor`.
- `vanth.agent_events` remains importable and emits data accepted by the Go daemon/monitor.
- Direct and wheel executables report the same version and pass checksum/provenance checks.
- No release depends on Windows Task Scheduler.

### Quality gates

- Unit, integration, differential, race, fuzz-smoke, chaos, soak, and packaging suites pass on their required matrix.
- `go vet`, formatting, Python compile, wheel build, and diff checks pass.
- No known unbounded goroutine, process, file-descriptor, database-connection, log, event, or in-memory-series growth remains.
- Security review confirms loopback binding, bearer authentication, restrictive metadata permissions, input limits, shell-free process invocation, and fail-closed future-schema behavior.

## 18. Release, Rollback, and Observability

- Keep rotating diagnostic logs bounded and include version, platform, home hash/path as appropriate, schema, operation, job/delivery ID, and error category.
- Never log bearer tokens, full sensitive environment values, or unbounded command output.
- `doctor --json` must be suitable for attaching to bug reports after secret redaction.
- Add a changelog section for database compatibility, native packaging, monitor keys, and known at-least-once delivery ambiguity.
- Before default cutover, demonstrate rollback by stopping Go, starting the Python daemon against the same schema-v5 fixture, and completing/recovering jobs safely.
- Do not bump to 1.0, tag, publish, or push as part of implementation unless separately authorized.
